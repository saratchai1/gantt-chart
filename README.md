# Integrated Master Gantt — โครงการพัฒนาแหล่งท่องเที่ยวห้วยขาแข้ง

Repository นี้พัฒนา **Integrated Master Schedule** จากแผนที่ 1–16 ของข้อเสนอ โดยใช้ไฟล์ `26.08.17 แผนงานก่อสร้างห้วยขาแข้ง หลัก.pdf` เป็น benchmark เฉพาะ **ระดับความละเอียดของ WBS / Activity Breakdown** เท่านั้น ไม่คัดลอกวัน ระยะเวลา หรือ logic ของตัวอย่างมาใช้เป็นฐานของแผนฉบับนี้

## Baseline v0.2

- Project duration: **1,200 project days**
- Contract installment structure: **497 installments**
- Generated detailed activities / gates: **874 rows**
- Milestones / gates: **95**
- Source-window / proposal critical-chain candidates: **106**
- Added explicit source-window convergence gates: **CP-05 D840** and **CP-06 D960**
- Plan-01 physical activities are now required by validation to have a downstream path to **D1200**
- Package handovers now require completion of parallel envelope / finish / furniture / external / specialist branches
- Network coverage, zero-float count and final connectivity are **recomputed on every build** and written to `data/validation-report.json` / `data/cpm-report.json`

> Detailed leaf durations and lags not explicitly stated in Plans 1–16 are proposal planning allowances. Activity provenance (`basis_type`) and exact timing provenance (`timing_basis`) are stored separately so a source-stated requirement cannot be mistaken for a source-stated duration/date.

> Baseline v0.2 deliberately does not hard-code a stale zero-float/connected-activity count in this README. Those values change whenever logic is tightened and are generated by `npm run validate` / `npm run export`.

## Schedule architecture

**Plan 01** is the physical-delivery backbone. **Plans 02–16** are integrated as predecessor gates, enabling activities, concurrent controls, inspection/evidence processes and closeout requirements.

Main source work-package bands:

- Installments 1–24 — preliminaries / enabling
- 25–317 — Area A
- 318–348 — Area B
- 349–383 — Area C
- 384–492 — Area D
- 493–497 — closeout / handover

The source-level critical control windows are retained:

- D1–90 survey / control / initial approval
- D31–180 temporary site systems / workfront readiness
- D31–270 design / approvals / long-lead procurement
- D181–600 main structure Area A
- D421–840 architecture / MEP Area A
- D301–960 Areas B/C/D + external systems
- D841–1080 landscape / detail completion / integration
- D1081–1200 commissioning / as-built / O&M / handover

### v0.2 project convergence

The source CP windows overlap, therefore they are not forced into one false global finish-to-start chain.

- `P01-CP05-GATE` — D840 source boundary for Area-A architecture / MEP completion
- `P01-CP06-GATE` — D960 source boundary for Areas B/C/D + external systems
- `P01-CO-001` — CP-07 D841–D1080 integration window

CP-07 starts after CP-05. CP-06 controls CP-07 **finish** because the source windows overlap. Individual Plan-01 package handovers also converge on CP-07 completion, including late Area-D landscape and raw-water-pontoon work.

## Integrated workfront readiness

The Area release network combines the controls stated across the plans. Before an Area workfront is released, the current baseline checks the relevant existing schedule activities for:

- site / temporary utility readiness
- HSE / JSEA / PTW readiness
- environmental readiness
- workforce competency / authorization readiness
- plant-personnel competency readiness
- traffic-management readiness
- controlled-document/CDE readiness
- QA/QC Method Statement / ITP readiness at package level
- Area D heritage/sensitive-workfront permit readiness

This converts Plans 03–11 from stand-alone bars into actual predecessor logic feeding physical construction.

## Physical package completion integrity

Detailed building packages use rolling workfronts and deliberately contain parallel branches. v0.2 makes handover wait for the relevant branches, not only the commissioning chain. Depending on package scope, the handover gate receives completion logic from:

- envelope / weather-tightness
- doors / glazing
- floor / final finish
- fixed furniture
- immediate external works
- specialist installations such as exhibition, kitchen, AV, process equipment or controls
- commissioning / functional test / punch / correction / as-built

External packages similarly close site furniture/signage and environmental monitoring evidence before handover.

## CPM / critical-path analysis

The schedule stores two different concepts:

1. `critical` — source-window / proposal critical-chain candidate used while constructing the baseline.
2. `computed_critical` — zero-float activity calculated from the actual predecessor network and the current D1200 final milestone.

Additional CPM fields exported per activity:

- `computed_total_float_days`
- `computed_free_float_days`
- `network_to_final`
- `driving_successor`

The proposal driving chain is traceable from NTP through the Area-A learning-centre structure/MEP/ICT/commissioning sequence, the CP-05 / CP-06 / CP-07 convergence, final installment packages 493–497, and the D1200 acceptance milestone. Detailed driving lags remain proposal assumptions unless explicitly source-stated.

This float analysis is calculated against the **current proposal bar placement and relationship network**. It is not represented as an approved contract CPM until the working calendar, approved detailed dates, production rates and vendor lead times are confirmed.

## Network validation

`npm run validate` now checks more than duplicate IDs and date ranges. It also reports:

- structural errors
- dependency cycles
- temporal relationship advisories
- overall D1200 network coverage
- Plan-01 physical network coverage
- Plan-01 package-handover network coverage
- unconnected Plan-01 physical activities

A Plan-01 physical activity that cannot reach the D1200 final milestone is treated as a **validation failure**. This prevents a visually complete Gantt bar from silently terminating outside the project-completion network.

## Interactive Gantt

Open `index.html` through a static web server or GitHub Pages. The viewer supports:

- Plan 01–16 filtering
- Zone and discipline filtering
- Activity basis: SOURCE / DERIVED / ASSUMPTION
- Timing basis: SOURCE timing / ASSUMED timing
- Computed zero-float critical-only view
- **Connected-to-D1200-only** view
- network-connectivity chip per activity
- Plan-01 physical network-coverage metric
- search by ID / WBS / building / activity / responsible party
- collapse / expand by Plan and Building/Area
- zoomed 1,200-day timeline
- click-through activity detail with predecessor logic, evidence, float, driving successor and network status
- CSV / JSON export from the browser
- validation / temporal / network-integrity visibility

Because the viewer uses ES modules, do not open it as a raw `file://` page if the browser blocks module imports. A simple static server is sufficient.


- `data/schedule-stats.json`

GitHub Actions runs JavaScript syntax checks, schedule validation and export, then uploads the generated files as an artifact.

## Source / assumption policy

- `basis_type = SOURCE` — activity/control requirement is explicitly stated by a source plan.
- `basis_type = DERIVED` — schedulable activity is decomposed from a source-defined process.
- `basis_type = ASSUMPTION` — proposal-level activity content had to be added to make the network usable.
- `timing_basis = SOURCE` — exact day/window is explicitly supported by source material.
- `timing_basis = ASSUMPTION` — exact detailed date/duration/lag is a proposal planning allowance.

The benchmark PDF is **never** used as a source of dates, durations or dependencies.
